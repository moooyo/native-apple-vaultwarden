# Tessera App, macOS App & AutoFill extension (Xcode-only)

This directory holds the **Xcode-only** targets — the iOS app, the macOS app, and the AutoFill
credential-provider extension. They need entitlements (App Groups, a shared Keychain access
group, the AutoFill capability) and code signing, which **SwiftPM cannot express**, so they live
in an Xcode project generated by [xcodegen](https://github.com/yonaskolb/XcodeGen) from
[`project.yml`](../project.yml) at the repo root.

The pure-Swift libraries stay in `Package.swift` and are tested headlessly (see below). The app
and extension targets only build inside Xcode on a machine with the full SDK + a provisioning
profile / device or simulator.

## Current implementation status

- `VaultStore` now links the official `SQLCipher.swift` **4.17.0** package directly. The shared
  database key is a random 32-byte Keychain secret, and opening the store verifies
  `PRAGMA cipher_version`; legacy plaintext system-SQLite caches use a guarded export/replace
  migration.
- App read/edit flows and repository payloads cover Login, Secure Note, Card, Identity, and SSH
  Key ciphers. Login passkeys, custom fields, item keys, and password revision dates are
  preserved where applicable.
- Password AutoFill, TOTP generation, passkey assertion, system password/passkey/OTP identities,
  and the real manual picker are present. Picker discovery is account-scoped and bounded; it
  filters passkeys by RP/allowed credential ids and decrypts secrets only after selection.
- Account-composite storage, API/repository generation leases, the cross-process session nonce,
  account-scoped outbox processing, and cold-start restoration of a locked session are implemented.
- Passkey registration uses a staging marker → shared-Keychain secret → atomic ready marker,
  replay-safe receipt/outbox import, and atomic sync finalization.

The 2026-07-16 final review tree passed all 14 runners (1305 checks), `swift build`, XcodeGen,
and unsigned Xcode 27 beta 2 builds of both app schemes. Signed-device behavior remains external.

## Local Mac without a developer account

Use the `OpenVault-Local` scheme for your own Mac on macOS 26 or later. It is sandboxed and signed
locally by Xcode. No team, provisioning profile, notarization, iPhone, or App Store submission is
needed. To build and install it for the first time, run from the repository root:

```sh
export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer
xcodegen generate
xcodebuild -project Tessera.xcodeproj -scheme OpenVault-Local -configuration Release \
  -destination 'platform=macOS' -derivedDataPath build/local build
mkdir -p "$HOME/Applications"
ditto build/local/Build/Products/Release/OpenVault.app "$HOME/Applications/OpenVault.app"
open "$HOME/Applications/OpenVault.app"
```

Sign in to your Vaultwarden server with a PBKDF2 account on first use. Manual copy, TOTP, sync
and master-password unlock use the regular app code. This edition does not install a system
AutoFill provider, publish credentials to macOS, or offer Touch ID unlock.

The local executable has no signing team. It keeps Hardened Runtime and embeds SQLCipher with
its original vendor signature. Its [library load constraint](macOS/Local/Libraries.coderequirement)
permits Apple platform code and Zetetic's `net.zetetic.SQLCipher` framework. No system-wide
security setting changes are required.

The SQLCipher database lives in the app's private sandbox. Its random key and session secrets
use the Mac's login Keychain under `dev.moooyo.tessera.local`, separate from the full edition.
On updates, quit and replace the app at the same path; keep its Keychain items and container.
macOS may ask for Keychain access again after rebuilding. If access fails, the app offers a retry
instead of opening an unencrypted database or resetting the vault.

To exercise the real login Keychain with disposable records and a fixture account, run
`OPENVAULT_TEST_LOGIN_KEYCHAIN=1 swift run VaultRepositoryTests`. The test removes its temporary
records; without the flag the runner does not access the login Keychain.

## Before you build

1. **Team:** in `project.yml`, set `DEVELOPMENT_TEAM` to your 10-character Apple Developer Team
   ID (or set it per-target / via an `.xcconfig`). It is intentionally left blank.
2. **Identifiers:** the placeholders below must all agree. If you change one, change them all:
   - bundle ids `dev.moooyo.tessera` (app) / `dev.moooyo.tessera.autofill` (extension) — in
     `project.yml` and the AutoFill `Info-AutoFill.plist` principal-class module.
   - App Group `group.dev.moooyo.tessera` — in every `*.entitlements` and
     `Sources/AppShared/AppShared.swift`.
   - shared Keychain access group `$(AppIdentifierPrefix)dev.moooyo.tessera.shared` — in every
     `*.entitlements`; Xcode expands the same prefix into each target's
     `OpenVaultKeychainAccessGroup` Info.plist value at signing time.
3. **Capabilities:** the App Group, the shared Keychain group, and "AutoFill Credential
   Provider" must be enabled on your App ID / provisioning profiles for the app **and** the
   extension. The Secure-Enclave biometric key + shared SQLCipher DB depend on these.
4. Pick the **Tessera-iOS** or **Tessera-macOS** scheme and build/run.

## Architecture notes

- **ServiceContainer wiring** (`AppEnvironment`): builds one `APIClient` (URLSession), opens the
  `VaultStore` on `tessera-vault.sqlite` inside the App Group container keyed by a random
  passphrase kept in the shared Keychain (so the extension opens the *same* DB), and composes
  the `ServiceContainer` (AuthRepository / VaultRepository / SyncEngine) plus an
  `ASCredentialIdentityWriter` so each sync rebuilds the AutoFill identity index. The apps inject
  the VM-facing `AuthService` / `VaultService` adapters into `RootView` / `MacRootView`.
  Foreground and lifecycle sync share one `SyncEngine` actor, preventing duplicate outbox sends.
- **Auto-lock:** the apps observe `scenePhase`; `AppEnvironment` enforces the deadline before
  foreground refresh and before background sync, so network work cannot extend key lifetime.
- **Background sync:** iOS registers a `BGAppRefreshTask` (`dev.moooyo.tessera.sync`, declared in
  `Info-iOS.plist` `BGTaskSchedulerPermittedIdentifiers`); macOS uses
  `NSBackgroundActivityScheduler`. Both run `flushOutbox` then `fullSync`.
- **The 120MB red line:** the AutoFill extension links **only** VaultReader, KeychainBridge,
  Fido2, DesignSystem, VaultModels, AppShared (+ transitive CryptoCore / KeyVault / VaultStore).
  `Generators` is linked transitively by `VaultReader` for TOTP; it links **no** Networking /
  SyncEngine / VaultRepository / UIShared / UI-*. The picker's identities are written by the
  *app* via `ASCredentialIdentityStore`; the extension scans only bounded display metadata and
  decrypts credential secrets for the ONE selected item.

## Testing

The app + extension require a **full-Xcode build**. Runtime acceptance still requires a signed
Simulator/device: enable the provider in Settings → Passwords, AutoFill a password and OTP into
Safari, then create and use a passkey. The libraries under `Sources/` are tested headlessly:

```sh
swift build                 # builds all library products (ignores App/)
swift run CryptoCoreTests   # and the other *Tests executable runners
```

(`swift build` does not touch this `App/` directory — those targets only exist in the Xcode
project, never in `Package.swift`.) There are 14 executable runners; all passed on the final
review tree (1305 checks).
